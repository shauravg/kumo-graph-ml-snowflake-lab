Predicting Repeat Customers with NVIDIA Kumo on Snowflake. No Feature Engineering, No Data Leaving the Platform.

A hands-on build: governed retail data, a semantic view, a graph neural network, and batch predictions, all inside Snowflake.

The retail question every marketing team asks

Which customers will buy again in the next 30 days?

It sounds simple. It drives real money: who gets the win-back email, who gets the discount, who you leave alone. And it's a question retailers have been answering the same way for years.

The traditional playbook:

  1. Join customers, orders, order items and products into one wide table.
  2. Hand-build features. Orders in the last 30, 60, 90 days. Average basket size. Days since last purchase. Favorite category.
  3. Train a gradient-boosted tree on that table.
  4. Rebuild most of it when the business asks the next question.

That works. It also throws information away. "4 orders in 90 days" says nothing about what was bought, in what order, or how those products behave across every other customer who bought them. Every feature is a guess about what matters, made by a person, before the model sees anything.

Why Kumo is different for this use case

Kumo skips the flattening step. It treats the database as what it already is: a graph.

  • Every row becomes a node. A customer, an order, an order line, a product.
  • Every foreign key becomes an edge. Order => customer. Order line => order. Order line => product.
  • A graph neural network learns directly across those connections, respecting time.

For retail repurchase that matters in three specific ways:

  • Product signal travels. A customer who bought products that other repeat buyers also bought carries signal a per-customer count never captures. That's two hops away in the graph. Painful to hand-engineer, natural for a GNN.
  • Sequence survives. The model sees individual orders with timestamps, not a pre-aggregated total.
  • New questions are cheap. Churn, next category, lifetime value. Change the prediction query, not the feature pipeline.

The prediction itself is one declarative statement in Kumo's Predictive Query Language (PQL):

PREDICT COUNT(ORDERS.*, 0, 30, days) > 0
FOR EACH CUSTOMERS.CUSTOMER_ID
WHERE COUNT(ORDERS.*, -90, 0, days) > 0

In plain English: for every customer who bought in the last 90 days, will they buy again in the next 30?

PQL looks like SQL. It isn't. It runs through Kumo, not the Snowflake SQL engine.

One honest caveat up front: this is a propensity score. It tells you who is likely to buy. It doesn't prove that sending an offer changes behavior. That's a different experiment.

The research and the launch behind it

None of this is new science. It's new packaging.

The method is called Relational Deep Learning, from the Kumo team and Stanford. Their paper frames a relational database as a temporal graph and trains GNNs on it directly. They also released RelBench, a public benchmark of 30 tasks across 7 real databases, comparing GNNs against an experienced data scientist hand-engineering features for LightGBM.

  • Kumo's intro to Relational Deep Learning: https://kumo.ai/research/relational-deep-learning-rdl/
  • The paper: https://arxiv.org/abs/2312.04615
  • RelBench explained: https://kumo.ai/research/relbench-guide/

On October 21, NVIDIA (which acquired Kumo earlier this year) launched the Kumo family of open models and the open-source Kumo Engine. Snowflake announced the same day that Kumo Engine runs on Snowflake ML. No separate Kumo account. No API key. Install the package in a Snowflake GPU runtime and go.

The quickstart shows the mechanics. I wanted to answer the next question: what does a properly governed version look like, the kind you could show a security team?

The architecture a real system needs

A notebook that trains a model isn't a system. Five things have to be true before anyone should trust the predictions:

  1. Governed inputs. The model only sees columns and customers it's allowed to see.
  2. One definition of the business. Relationships are defined once, not re-typed in every notebook.
  3. GPU compute without a separate platform. No extra account, no data copied out.
  4. Model lifecycle. Versioned, reloadable, auditable.
  5. Honest evaluation. Later dates than training. A simple baseline on the same customers.

Here's how Snowflake components map to each:

Governed inputs => secure views, masking and roles

Raw tables sit in a RAW schema. Secure views in a GOVERNED schema expose only approved columns and only ML-eligible customers, including their orders and items, so excluded customers can't sneak back in as graph neighbors. Names and emails live in a separate identity table with a masking policy. The ML role can't read RAW at all.

Advantage: access control is the same RBAC you already run. Not a new system to audit.

One definition => a Snowflake semantic view

The semantic view RETAIL_CUSTOMER_360 declares the tables, keys and the three relationships. Analysts use it for reporting. The pipeline reads the same definition with DESCRIBE SEMANTIC VIEW, validates it in SQL, and builds the Kumo graph from it.

Advantage: one relationship definition, two uses. Report what happened. Predict what happens next.

GPU compute => Snowflake ML Jobs on a GPU compute pool

The training code runs as a Snowflake ML Job on a dedicated single-node GPU pool (NVIDIA A10G). A PyPI-only external access integration lets it install kumo-engine. It authenticates with the runtime's own identity.

Advantage: no separately managed infrastructure outside Snowflake. The pool auto-suspends.

Model lifecycle => Snowflake Model Registry and Experiment Tracking

Every trained model is published as a new version in the Model Registry, then reloaded by exact version for scoring. Parameters, the semantic definition's fingerprint and holdout metrics go to Experiment Tracking.

Advantage: "which model made this prediction?" has a query-able answer.

Honest evaluation => SQL

Labels, training populations, the baseline, output validation and every metric are SQL. Python only does what only the Kumo SDK can do.

Advantage: the logic that decides whether the model is any good is readable, reviewable and runs on a warehouse.

One more thing worth saying plainly. "No separately managed infrastructure" isn't "no infrastructure." There's still a warehouse, a GPU pool, packages and grants. And it isn't zero-copy: Kumo materializes a graph snapshot in the runtime. Changing a masking policy later doesn't erase an existing snapshot or what a model already learned. Those artifacts need their own lifecycle.

The flow, end to end

                                               graph => train => register

                                                      ▼

                                               restricted result tables

Step by step:

  1. Generate and govern (SQL). Synthetic customers, orders, items and products land in RAW. Secure views filter them to approved columns and eligible customers.
  2. Define semantics (SQL). A native semantic view declares the three relationships.
  3. Validate (SQL). A procedure reads the semantic view, rejects anything outside an approved column list, checks keys and foreign keys against the data, and returns a manifest with a fingerprint. Change the semantic view mid-run => the run stops.
  4. Prepare (SQL). Training labels at monthly anchor dates, a validation month and a test month, plus scoring populations and a purchase-frequency baseline.
  5. Train (Python, Kumo SDK). Build the graph from the manifest, snapshot it, train one bounded run (5 epochs), and publish to the Model Registry.
  6. Score (Python, Kumo SDK). Reload the exact model version. Build a fresh snapshot for each scoring date and predict.
  7. Finalize (SQL). Check every expected customer got exactly one valid score, write normalized result tables, and compute holdout metrics.

Why time is the hard part

[IMAGE: screenshot of section 04 timeline from article/workflow.html]

  Apr ─────── Nov 2025   Jan 1    Mar 1   Apr 1     May 31    Jun 30
  └─ training anchors ─┘  valid.   test   fit cut   HOLDOUT   CURRENT
                                          off       (scored,  (scored,
                                                     graded)  no labels)

Leakage is the classic way a churn model looks brilliant in a notebook and useless in production. So:

  • Training data stops at April 1. The holdout period never enters training.
  • Each scoring date gets its own fresh snapshot, cut off at that date. May 31 scoring sees nothing from June, the month it's predicting.
  • The holdout batch is graded against what customers actually did. The current batch is the real output: no labels, because it's the future.

What the run showed

All data is synthetic. Both models scored the same 6,476 holdout customers as of May 31. Then we checked who actually bought in June: 43% did.

Kumo graph model

  • AUROC: 0.705
  • Average precision: 0.632
  • Top-10% lift: 1.70x
  • Brier score: 0.273

Purchase-frequency baseline

  • AUROC: 0.638
  • Average precision: 0.549
  • Top-10% lift: 1.49x
  • Brier score: 0.246

How to read these numbers

The metrics answer two different questions. A model can be good at one and bad at the other.

Question 1: does it put likely buyers first? (ranking)

  • AUROC. Pick one customer who bought and one who didn't. How often does the model score the buyer higher? 0.5 is a coin flip, 1.0 is perfect. Kumo gets that pair right about 70% of the time, the baseline about 64%. Solid for a 30-day purchase prediction. Not magic.
  • Top-10% lift. The most business-friendly number. Take the top-scored 10%, about 650 customers. Kumo's group bought again at about 73%, against a 43% average. The baseline's group bought at about 64%. Same email budget => roughly 60 more actual buyers on Kumo's list.
  • Average precision. How pure the list stays as you work down it. Random ordering would score 0.43, the base rate. Both beat random; Kumo by more.

Question 2: are the probabilities honest? (calibration)

  • Brier score. The average squared gap between the predicted probability and what happened. Lower is better.
  • The useful yardstick: give every customer the same 43% score and you get 0.245.
  • The baseline lands right on that yardstick. Kumo lands above it.
  • So Kumo's ordering is better, but its probability numbers are systematically off. Likely reasons: training months had different purchase rates, only 5 epochs, and no calibration step.

What that means in practice

  • Do use Kumo's scores to sort customers. "Target the top 20%" is the right kind of decision.
  • Don't use a raw score as a probability yet. "73% likely, so spend up to $X" would mislead you.
  • Fix it with a calibration step (Platt scaling or isotonic regression) fitted on the validation month. Ranking stays, numbers become trustworthy.

How much to read into it

  • Synthetic data. It proves the pipeline works, not the size of the gain on a real retailer.
  • One run. No confidence intervals or repeats. A 0.067 AUROC gap on 6,476 customers is probably real, but I didn't measure the uncertainty.
  • Simple baseline. A purchase-frequency count, not a tuned gradient-boosted model. Beating it is a floor.
  • Propensity, not impact. These scores say who will buy, not who will buy because you contacted them. That needs a holdout campaign.

Run facts: one NVIDIA A10G, kumo-engine 1.0.0, 5 training epochs, about 5 minutes for the successful job. 6,217 current customers scored, none missing, no names or emails anywhere in the outputs.

Two things broke on the way, both worth knowing. Kumo rejected decimal-number keys, and it rejected a decimal-typed split column. Both fixed by casting in SQL: keys to strings, the split to a float.

Hands-on lab: run it yourself

[INSERT LINK TO CODE REPOSITORY]

What you need

  • A Snowflake account with ACCOUNTADMIN for the one-time setup
  • GPU compute pool access (GPU_NV_S)
  • Python 3.12 locally with snowflake-ml-python, plus the Snowflake CLI
  • About 30 minutes, most of it waiting on the GPU

Step 1: Set up roles, compute and governance

Review and run sql/01_setup_review.sql. It creates four roles (owner, identity steward, ML, reader), an X-Small warehouse, a single-node GPU pool, a PyPI-only network integration, the RAW and GOVERNED objects, and the masking policy. Before running anything, replace the demo account name (a safety guard in the SQL scripts and job_entry.py) with your account name, and the user in the grants with yours.

Step 2: Generate the synthetic data

Run sql/03_generate_synthetic.sql as KUMO_DEMO_OWNER. Deterministic, about 30 seconds. It refuses to run against tables that already have data.

Step 3: Create the semantic view

Run sql/04_semantic_view.sql, then sql/02_semantic_queries.sql for grants and a few descriptive queries. Try it:

SELECT * FROM SEMANTIC_VIEW(
  KUMO_SEMANTIC_DEMO.SEMANTIC.RETAIL_CUSTOMER_360
  METRICS ORDERS.SALES);

Step 4: Install the SQL pipeline

Run sql/05_contracts.sql, sql/06_prepare.sql and sql/07_finalize.sql, in that order, as KUMO_DEMO_OWNER.

Step 5: Prove the governance

Run sql/08_acceptance.sql. You should see the owner role get 0 visible names, the steward see all of them, and the ML role pass its data checks. The last call returns the semantic manifest. Copy its semantic_hash. That's your approval of exactly what the model will see.

Step 6: Train and score on the GPU

From the repo root:

python submit_job.py <semantic_hash> sql-v2

It uploads the code, runs it as a Snowflake ML Job on the GPU pool, waits, and prints the logs.

Step 7: Look at the results

SELECT run_id, status, model_version
FROM KUMO_SEMANTIC_DEMO.RESULTS.V2_RUNS;

CALL KUMO_SEMANTIC_DEMO.RESULTS.V2_EVALUATE(
  '<your account name>',
  'KUMO_SEMANTIC_DEMO.RESULTS.RETAIL_HOLDOUT_<run_id>');

Then open the Model Registry and Experiment Tracking in Snowsight and find your run.

Step 8: Clean up

Suspend the pool and warehouse when you're done. To remove everything, run sql/99_cleanup.sql as ACCOUNTADMIN. It's irreversible: data, models and predictions all go.

Takeaways

  • For relational problems like repurchase, a GNN on the raw graph skips the feature-engineering cycle and kept more signal than a frequency baseline in this demo.
  • Kumo Engine on Snowflake means the GPU work happens next to governed data, under the same roles and audit trail.
  • Define relationships once in a semantic view. Use them for analytics and for ML.
  • Keep evaluation logic in SQL, and check calibration before acting on probabilities.

Synthetic data. Results describe this demo, not a measured business outcome.
